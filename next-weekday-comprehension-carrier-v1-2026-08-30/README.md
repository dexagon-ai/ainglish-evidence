# `next-up` / `next-week` comprehension carrier v1

This package freezes the missing original comprehension carrier for the everyday “next Friday”
distinction. It makes no model call and files no measurement. Execution remains sealed until the
live proposal still requests the original, this exact packet is committed, and at least two
independent reader lineages pass the same construct-free qualification packet.

Four primary campaigns preserve both forms and both comparisons separately:

- `next-up` versus its full careful-English mapping;
- `next-up` versus the ambiguous bare “next weekday” instruction;
- `next-week` versus its full careful-English mapping;
- `next-week` versus the byte-identical ambiguous bare instruction.

Each campaign contains 196 exact joint date-and-offset items: four seven-day anchor weeks crossed
with all seven target weekdays. The four epochs cover leap-day, year, month, and ordinary
boundaries; Monday- and Sunday-start conventions contribute 98 items each. Exactly 84 cells are
load-bearing because the constructors select different dates. The other 112 are convergent
controls and must be reported separately, never allowed to dilute the primary divergent stratum.
Correct option positions are balanced 49/49/49/49.

The two bare campaigns use identical English bytes for every scenario. Their correct answers differ
on exactly the 84 divergent cells, so a reader cannot earn credit in both hidden intended worlds by
adopting one fixed interpretation of “next Friday.” The marked and careful arms explicitly bind the
anchor date, target weekday, and—where applicable—the week-start convention.

Separate 70-item packets for each form test the registered nonclaims: no time of day, timezone,
recurrence, deadline-inclusion rule, or business-day adjustment is supplied. These secondary rows
never enter primary comprehension accuracy.

Rebuild and audit offline:

```bash
python3 next-weekday-comprehension-carrier-v1-2026-08-30/build.py
python3 next-weekday-comprehension-carrier-v1-2026-08-30/audit.py
```

Present reader and tokenizer performance reflects systems trained primarily on ordinary English,
not systems trained on ratified Ainglish. That asymmetry belongs beside later results but cannot be
used to reverse an observed favourable, null, or adverse result.
